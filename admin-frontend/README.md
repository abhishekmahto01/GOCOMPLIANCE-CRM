# GoCompliances CRM - Admin Panel Frontend (Stage 7D)

A dedicated, standalone React + Vite + TypeScript administrative panel for managing GoCompliances CRM employees, organizational hierarchies, and status workflows.

---

## 1. System Architecture & Port Allocation

The GoCompliances CRM system operates across dedicated services:

| Service | Port / URL | Description |
| :--- | :--- | :--- |
| **Admin Panel Frontend** | `http://localhost:8001` | Dedicated administrative & employee management interface |
| **Main CRM Frontend** | `http://localhost:5173` | Main operational CRM frontend |
| **FastAPI Backend API** | `http://localhost:8000` | REST API with JWT authentication & server-side RBAC |
| **PostgreSQL Database** | `localhost:5432` | Relational database (`is_gocompliance_db`) |

---

## 2. Prerequisites

- **Node.js**: v18+ (tested on Node 20 / 22 / 24)
- **npm**: v9+
- **FastAPI Backend**: Running on `http://localhost:8000`
- **PostgreSQL**: Active on `localhost:5432`

---

## 3. Installation & Setup

1. Navigate to the `admin-frontend/` directory:
   ```bash
   cd admin-frontend
   ```

2. Install dependencies:
   ```bash
   npm install
   ```

3. Configure environment variables:
   Copy `.env.example` to `.env` (or configure `VITE_API_BASE_URL`):
   ```bash
   cp .env.example .env
   ```

   **Environment Variables:**
   ```env
   VITE_API_BASE_URL=http://localhost:8000
   ```

## 5. Application Routing

| Route | Page | Description | Permission Requirement |
| :--- | :--- | :--- | :--- |
| `/login` | Admin Login | Sign in with employee code or email | Public |
| `/` | Admin Dashboard | Overview metrics, quick actions & module permissions | Authenticated |
| `/employees` | Employee Directory | Paginated employee table, search & dependent filters | `ADMIN_EMPLOYEES:view` |
| `/employees/new` | Add Employee | Create employee with cascading dropdowns | `ADMIN_EMPLOYEES:create` |
| `/employees/:userId` | Employee Details | Comprehensive employee profile & status history | `ADMIN_EMPLOYEES:view` |
| `/employees/:userId/edit` | Edit Employee | Update employee profile (read-only employee code) | `ADMIN_EMPLOYEES:edit` |
| `/unauthorized` | Access Denied | Friendly 403 screen with navigation | Authenticated |
| `*` | 404 Not Found | Catch-all for undefined routes | Public / Authenticated |

## 6. Permission & Security Model

The Admin Panel adheres strictly to server-enforced permissions and data scopes:

- **Permission Enforcement (`ADMIN_EMPLOYEES`)**:
  - `can_view`: Grants access to `/employees` directory and `/employees/:userId` details page.
  - `can_create`: Displays and activates "Add Employee" button and `/employees/new` route.
  - `can_edit`: Displays and activates "Edit Employee" action buttons and `/employees/:userId/edit` route.
  - `can_approve`: Displays and activates "Status" update action dialog (`PENDING`, `ACTIVE`, `INACTIVE`, `SUSPENDED`).
  - `can_delete`: Not displayed (hard delete is disabled by system architecture).

- **Data Scopes**:
  - `SELF`: User only sees their own profile.
  - `TEAM`: User sees subordinates within their reporting hierarchy.
  - `DEPARTMENT`: User sees employees within their department.
  - `COMPANY`: User sees employees within their company.
  - `ALL`: Admin/Director sees all records across all 3 group companies.

- **Security Safeguards**:
  - No client-side employee code creation (atomically generated by backend).
  - No plaintext passwords or salary details requested or exposed.
  - Automatic session teardown and redirect on HTTP 401.
  - Request headers carry `Authorization: Bearer <access_token>`.

## 7. Dependent Cascading Dropdowns

Form selectors dynamically query backend lookup APIs:
1. **Company Selector**: Fetches active companies (`/api/admin/lookup/companies`).
2. **Department Selector**: Queries `/api/admin/lookup/departments?company_id={id}` based on the selected company.
3. **Designation Selector**: Queries `/api/admin/lookup/designations?company_id={id}` based on the selected company.
4. **Reporting Manager Selector**: Queries active employees for the company (`/api/admin/lookup/managers?company_id={id}`), excluding the employee themselves in edit mode to prevent circular reporting hierarchies.
